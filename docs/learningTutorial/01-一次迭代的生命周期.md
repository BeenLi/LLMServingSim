## 2. 主循环到底是什么

不是离散事件轮，而是**跟 ASTRA-Sim 子进程做阻塞式行 IPC 的 while 循环**（[`__main__.py:550`](../../serving/__main__.py#L550)）。一次循环 = 一次迭代：

```
                 ┌──────────────────────────────────────────────┐
                 │  ASTRA-Sim (C++ 子进程, stdin/stdout)         │
                 └──────────────────────────────────────────────┘
   read_wait ─────────▲                                    │
   阻塞到读到 "Waiting"│                                    │ 打印
                      │                                    ▼
   parse_output ──────┴── "sys[0] iteration K finished, C cycles,
                           exposed communication E cycles."
        │
        ├─ current = C                     ← 全局时钟由 ASTRA-Sim 驱动
        ├─ router.route_arrived_requests(current)
        ├─ scheduler.add_done(K, ...)      ← 注意 `id -= 1`：iteration K ↔ batch K−1
        ├─ scheduler.schedule(current)     → Batch 或 None
        ├─ generate_trace(batch)           → inputs/runs/<id>/trace/…/instance0_batchN.txt
        ├─ generate_graph(batch)           → chakra 子进程 → …/workload/…/llm.0.et
        └─ write_flush(p, workload)        → 把 .et 路径写回 ASTRA-Sim stdin
                                             （没 batch 可跑就写 "pass"）
```

代码锚点：
- [`controller.py:13`](../../serving/core/controller.py#L13) `read_wait()` —— 死循环 `p.stdout.readline()` 直到行里出现 `Waiting` 或 `Checking Non-Exited Systems ...`
- [`controller.py:39`](../../serving/core/controller.py#L39) `parse_output()` —— 正则抓 `sys / iteration / cycles / exposed communication`
- [`__main__.py:558`](../../serving/__main__.py#L558) `current = out_dict['cycle']`
- [`scheduler.py:669`](../../serving/core/scheduler.py#L669) `id -= 1` —— **ASTRA-Sim 的 iteration 编号比 batch_id 大 1**，因为第 0 次 iteration 是 event handler（把时钟推进到第一个请求的 arrival）
- [`__main__.py:600`](../../serving/__main__.py#L600) `schedule()` → [`__main__.py:751`](../../serving/__main__.py#L751) `generate_trace()` → [`__main__.py:764`](../../serving/__main__.py#L764) `generate_graph()` → [`__main__.py:769`](../../serving/__main__.py#L769) `get_workload()`

## 3. 三种迭代形态

`example_trace.jsonl` 的请求 0 是 `input=10, output=70, arrival=46926808`。日志里挑三个 batch：

| batch | 组成 | `total_len` | trace 里 `attention_4` 的 `comp_time` |
|---|---|---|---|
| #0 | 纯 prefill：req0 的 10 个 prompt token | 10 | 7985 ns |
| #1 | 纯 decode：req0 生成第 2 个 token | 1 | 8352 ns |
| #28 | **混合**：req0 decode 1 tok + req1 prefill 22 tok | 23 | 15240 ns |

batch #28 就是 continuous batching + chunked prefill 的直接证据 —— 新到的 req1 不必等 req0 跑完，直接插进同一次前向。调度顺序是 [`scheduler.py:113`](../../serving/core/scheduler.py#L113) 的 `batch_req = decodes + prefills`（decode 先排，各占 1 token；prefill 再按剩余 token budget 切 chunk）。

145 次真实迭代的 batch 规模分布：

```
num_reqs=1 : 38    num_reqs=4 : 20    num_reqs=7 : 30
num_reqs=2 : 11    num_reqs=5 :  2
num_reqs=3 : 11    num_reqs=6 : 33
```

- 首行 `COLOCATED` = `pd_type`（非 PD 分离），`model_parallel_NPU_group` = `pp_size`（[`trace_generator.py:1549`](../../serving/core/trace_generator.py#L1549)）

### 张量尺寸都能手算出来

Llama-3.1-8B / bf16：`hidden=4096`，`kv_heads×head_dim = 8×128 = 1024`，`vocab=128256`。

| 字段 | 公式 | batch0 (`total_len=10`) | batch1 (`total_len=1`) | batch28 (`total_len=23`) |
|---|---|---|---|---|
| `embedding.input_size` | `total_len × 4 B`（int32 token id） | 40 ✓ | 4 ✓ | 92 ✓ |
| hidden 张量 | `total_len × 4096 × 2 B` | 81920 ✓ | 8192 ✓ | 188416 ✓ |
| `qkv_proj.output_size` | `total_len × (4096+2×1024) × 2 B` | 122880 ✓ | 12288 ✓ | 282624 ✓ |
| `attention.input_size` | `q_bytes + Σ_decode(num_computed_tokens) × 4096 B` | 81920 ✓ | 8192 + 10×4096 = **49152** ✓ | 23×8192 + 37×4096 = **339968** ✓ |
| `sampler.input_size` | `total_len × 128256 × 2 B` | 2565120 ✓ | 256512 ✓ | 5899776 ✓ |

`4096 B/token` = `2(K,V) × 1024 × 2 B`。batch28 里的 `37` 是 req0 此刻的 `num_computed_tokens`（10 个 prompt + 27 次 decode）—— 全部对上。

## 5. 数值验证一：`cycle` 从哪来

**恒等式**（本阶段最重要的发现）：

```
cycle(K) − cycle(K−1)  ==  Σ comp_time(batch K−1)  +  [exposedComm(K) − exposedComm(K−1)]
```

⚠️ ASTRA-Sim 打印的 `cycles` 和 `exposed communication` **都是累计值**，不是单次迭代值。日志：

```
NPU[0] iteration 0  finished,  46926808 cycles, exposed communication     0 cycles.
NPU[0] iteration 1  finished,  57935078 cycles, exposed communication 10020 cycles.
NPU[0] iteration 2  finished,  69082897 cycles, exposed communication 11022 cycles.
NPU[0] iteration 28 finished, 358971567 cycles, exposed communication 37074 cycles.
NPU[0] iteration 29 finished, 370729151 cycles, exposed communication 60120 cycles.
```

```bash
# Σ comp_time
for b in 0 1 28; do
  awk 'NR>3 {s+=$2} END {print s}' .../instance0_batch${b}.txt
done
# → 10998250 / 11146817 / 11734538
```

| | Δcycle | Σcomp_time | ΔexposedComm | 核对 |
|---|---|---|---|---|
| iter1 (batch0) | 57935078−46926808 = 11008270 | 10998250 | 10020−0 = 10020 | ✓ |
| iter2 (batch1) | 69082897−57935078 = 11147819 | 11146817 | 11022−10020 = 1002 | ✓ |
| iter29 (batch28) | 370729151−358971567 = 11757584 | 11734538 | 60120−37074 = 23046 | ✓ |

三条全部**逐位相等**。

`iteration 0` 的 46926808 就是 req0 的 `arrival_time_ns` —— event handler 把时钟推到第一个请求到达。而 iter1 的 Δ = 11008270 正是 CSV 里 req0 的 `TTFT`。**从 trace 到 CSV 指标的链路闭合。**

### exposed communication 是什么

TP=1、`comm_type` 全 NONE，哪来的通信？答案是 `REMOTE:0` 的内存搬运。整份 trace 里只有两行带 REMOTE：首层 `embedding` 的 input、末层 `sampler` 的 output。Chakra 的 LLM 转换器为这两处各建一个 `MEM_LOAD_NODE` / `MEM_STORE_NODE`（`llm_converter.py:328` / `:541`），ASTRA-Sim 按 `memory/memory_expansion.json` 的带宽算时间：

```json
{ "remote_mem": { "memory-type": "PER_NODE_MEMORY_EXPANSION",
                  "mem-bw": 256, "mem-latency": 0, "num-devices": 1 } }
```

`mem-bw = 256` GB/s = 256 B/ns。

**但 store 节点的大小取错了字段。** `llm_converter.py:541-546`：

```python
output_store_node = self.get_memory_store_node(
    layers[layer_end - 1].name,
    "OUTPUT",
    layers[layer_end - 1].output_memory_loc,    # REMOTE:0        ← 对
    layers[layer_end - 1].input_memory_size,    # sampler 的 input ← 不是 output！
)
```

`sampler` 的 `output_size` 是 40 B（`total_len × 4`，采样出的 token id），而它的 `input_size` 是 2565120 B（`total_len × vocab × 2`，整张 logits）。转换器传的是后者，于是：

| batch | 末层 `input_size`（被当成 store 大小） | ÷256 | 实测 ΔexposedComm |
|---|---|---|---|
| #0 | 2565120 | 10020 | 10020 ✓ |
| #1 | 256512 | 1002 | 1002 ✓ |
| #28 | 5899776 | 23046 | 23046 ✓ |

三个都整除。（首层 `embedding` 的 REMOTE 读只有 40/4/92 字节，`/256` 不足 1 ns，取整成 0。）

**影响**：`exposed communication` 实际正比于 `total_len × vocab_size × 2 / 256`，而非应有的 `total_len × 4 / 256` —— 放大了 **64128 倍**。本次实验里它只占迭代耗时的 0.09%（batch0：10020 / 11008270），可以忽略；但它随 `total_len` 线性增长，若把 `--max-num-batched-tokens` 拉满到 2048，这一项就是 `2048 × 128256 × 2 / 256 ≈ 2.05 ms`，在一次几十毫秒的 prefill 迭代里已是百分之几的量级。记在这里，等阶段 6 拿 bench 对齐真机时回来验证。

> 这一处在 `astra-sim` submodule（chakra，commit `f82fb3d`）里，不是 `serving/` 的代码。

## 6. 数值验证二：`comp_time` 从哪来

全部来自 `profiler/perf/RTXPRO6000/meta-llama/Llama-3.1-8B/bf16/tp1/*.csv`（单位微秒，加载时 ×1000 转纳秒）。这是阶段 3 的正题，这里先建立"数字能对上"的信心：

**`lm_head` ← `per_sequence.csv`（按请求数，不是 token 数）**

```
layer,sequences,time_us
lm_head,1,714.006     → batch0 (1 req) 的 lm_head_290 = 714006 ✓
lm_head,2,687.06      → batch28 (2 req) 的 lm_head_290 = 687060 ✓
```

> 注意 `n=2` 比 `n=1` 更快 —— profile 噪声，不是笔误。

**`attention` ← `attention.csv` 的 4D log-linear 插值**（[`_lookup_attention`](../../serving/core/trace_generator.py#L759)）

batch1（`prefill_chunk=0, kv_prefill=0, n_decode=1, kv_decode=10`）：表里最小的 `kv_decode` 样本是 16，低端 clamp（[`_axis_bracket:541`](../../serving/core/trace_generator.py#L541)），直接命中

```
0,0,1,16,8.35233   → 8352 ns ✓
```

batch0（`prefill_chunk=10, kv_prefill=0, n_decode=0`）就没这么直白了 —— 手算：

- `pc_vals = [0, 16, 24, 32, 36, 54, 64, 81, …]`，`pc=10` 落在 `[0,16]`。因为下端是 0，`_axis_bracket` 退化为**线性**：`t_pc = 10/16 = 0.625`
- `nd=0` → `lo=hi=0`, `t_nd=0`
- 角点 `(pc=0, nd=0)` 在表里不存在 → 回退到欧氏最近的 `(0,1)`，查得 `8.35233`
- 角点 `(pc=16, nd=0)` → `7.76533`
- `8.35233 + 0.625 × (7.76533 − 8.35233) = 7.985455 µs` → `int()` → **7985 ns** ✓

和 trace 里的 `attention_4  7985` 一致。

> 所以 `_lookup_attention` 在**四个轴上都插值**（两端为正走 log 空间，某端为 0 退化线性，越界时低端 clamp、高端 log 外推），最近邻只是 `(pc, nd)` 缺角时的兜底。

## 7. 顺手发现的三处细节

1. **末层 store 大小取错字段**（见 §5）。`llm_converter.py:545` 用 `input_memory_size` 当 `OUTPUT` store 的大小，使 `exposed communication` 正比于 logits 而非 token id。

2. **`lm_head` / `sampler` 的时间按序列数查表（对），但张量尺寸按 `total_len` 记。** 真实 vLLM 只对每个序列的最后一个 token 算 logits，这里对全部 token 记了尺寸。`comp_time` 不受影响（走 `per_sequence.csv`），但它和上一条叠加，共同决定了那个被放大的 `exposed communication`。

3. **`--cleanup-inputs` 默认开启**，跑完删掉整个 `runs/<run_id>/`。想留 trace 必须显式 `--no-cleanup-inputs`。而 `astra-sim/inputs/trace/` 下若有同名旧文件，那是历史遗留 —— **不要拿它当本次运行的产物**（本次踩过：`ls -l` 显示 mtime 是三周前的，差点据此得出错误结论）。

## 8. 检查点自测

> 能用自己的话讲清"从一个 `.jsonl` 请求到 CSV 里一行指标"中间经过了哪几个模块、每个模块的输入输出是什么。

- `router.load_requests` 读 jsonl → `Request(input, output, arrival)`
- `router.route_arrived_requests(current)` 按负载投递给某个实例的 `scheduler.request` 队列
- `scheduler.schedule(current)` 在 `max_num_seqs` / `max_num_batched_tokens` / KV 显存三重预算下，把 decode + chunked prefill 凑成一个 `Batch`（`q_list / decode_k_list` 就是给 attention 4D 查表用的）
- `generate_trace(batch)` 沿 `profiler/models/llama.yaml` 的 `sequence:` 逐层查表 → 292 行文本 trace
- `generate_graph` 起 chakra 子进程 → `llm.0.et`
- `controller.write_flush` 把 `.et` 路径喂给 ASTRA-Sim；ASTRA-Sim 算完打印累计 `cycles`
- `scheduler.add_done` 更新 `num_computed_tokens`；prefill 收尾时 `req.set_ttft(finish)`（[`scheduler.py:723`](../../serving/core/scheduler.py#L723)），decode 每步 `req.add_itl(finish)`
- 请求结束 → `req.add_latency(end_time)` 算出 `tpot = (latency − ttft) // (output − input − 1)`（[`request.py:55`](../../serving/core/request.py#L55)）→ 落 CSV
