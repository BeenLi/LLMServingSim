## 0. 先建立心智模型（半天）

### 0.1 这是什么

LLMServingSim 是一个**迭代级（iteration-level）的 LLM 推理服务模拟器**。它不真跑 GPU kernel，而是：

- 用 **profiler** 在真实 vLLM 上测出每类算子在目标硬件上的延迟表（CSV）；
- 用 **serving（Python 前端）** 复现 vLLM 式的连续批处理调度，每个迭代查延迟表拼出一条「执行 trace」；
- 把 trace 交给 **ASTRA-Sim（C++ 后端）** 算出这次迭代的 cycle 数（尤其是并行通信/内存搬运）；
- 用 **bench** 拿真机 vLLM 跑同样 workload 做端到端校验。

一句话：**profiler 提供"算得多快"，ASTRA-Sim 提供"通信/搬运多慢"，serving 负责"这一步该算什么"，bench 负责"和真机差多少"。**

### 0.2 五件套与数据流（务必记住这张图）

```
profiler/perf/<hw>/<model>/<variant>/tp<N>/*.csv   ← 真实 vLLM CUDA kernel 计时
        │  _load_perf_db() + 各类 _lookup_*()
        ▼
serving/core/trace_generator.py  →  文本 trace 文件（每层一行：comp_time / 通信类型 / 内存位置）
        │  Chakra 转换器（graph_generator.py 起子进程）
        ▼
*.et（protobuf 图）
        │  stdin/stdout IPC（controller.py）
        ▼
ASTRA-Sim (C++)  →  这次迭代的 cycle 数
        │
        ▼
serving/core/scheduler.py  →  更新请求状态、进入下一迭代
```

对应代码：主循环 `serving/__main__.py:550`（"one while loop processes one iteration"）；调度 `scheduler.py:55`；拼 trace `trace_generator.py:1448`；起 Chakra 子进程 `graph_generator.py:26`；与 ASTRA-Sim 的 IPC `controller.py:13`（读）/ `controller.py:32`（写）。

## 1. 单实例：一次迭代的生命周期（1–2 天）

**概念铺垫（serving 侧，从零）**
- 一个请求分两个阶段：**prefill**（把整段 prompt 一次算完，产出第 1 个 token，决定 **TTFT**）与 **decode**（逐 token 自回归，每步耗时决定 **TPOT/ITL**）。
- LLM serving 是 **iteration-level scheduling**：不是"一个请求跑到底"，而是每个迭代把当前活跃请求凑成一个 batch 一起前向一步。

**建模侧：一次 while 迭代都干了啥**（跟着 `serving/__main__.py:550` 主循环读）
1. `router` 把到点的请求投递给实例（`__main__.py:593` 处理完成回调）；
2. `scheduler.schedule()`（`__main__.py:600` → `scheduler.py:55`）在显存/token 预算下凑出这一步的 batch；
3. `generate_trace(...)`（`__main__.py:647/714/751` → `trace_generator.py:1448`）查延迟表拼出 trace；
4. Chakra 转 `.et`，`controller` 喂给 ASTRA-Sim 并读回 cycle；
5. `scheduler` 更新请求状态、标记完成；到达终止条件（`__main__.py:897`）退出。

**代码锚点**：`request.py`（Request/Batch 数据类）、`scheduler.py:18` `class Scheduler`、`controller.py:13/32`（IPC 收发）。

**动手**：把 `--log-level INFO`（甚至 `DEBUG`）打开重跑上面的命令，观察每迭代的 batch 组成、prefill→decode 的切换、显存变化。

**检查点**：能用自己的话讲清"从一个 `.jsonl` 请求到 CSV 里一行指标"中间经过了哪几个模块、每个模块的输入输出是什么。

## 2. 调度与 KV 缓存（2–3 天）

**概念铺垫**
- **Continuous batching**：请求完成即腾位、新请求随时插入，不等整批结束。
- **Chunked prefill**（默认开）：长 prompt 的 prefill 拆成多迭代，避免一个长请求独占 token 预算。旋钮：`--max-num-batched-tokens`（每迭代总 token 上限，默认 2048）、`--max-num-seqs`（batch 内最大序列数，默认 128）、`--long-prefill-token-threshold`（单请求每步 token 上限）。
- **KV 缓存分页**：KV 以 `--block-size`（默认 16）token 为块管理（PagedAttention 思想）。
- **Prefix caching（RadixAttention，默认开）**：相同前缀的 KV 块复用，用基数树组织。

**建模侧锚点**
- 连续批处理 + chunked prefill 的调度主体：`scheduler.py:55` `schedule()` → `scheduler.py:69` `schedule_base()`，chunked 分支 `scheduler.py:110`。
- 前缀缓存基数树：`radix_tree.py:134` `class RadixCache`、`radix_tree.py:237` `match_prefix()`、`radix_tree.py:74` `TreeNode`（源自 SGLang）。
- 显存/KV 记账：`memory_model.py:16` `class MemoryModel`，KV 分页与前缀事件 `memory_model.py:64` 起。

**动手对比实验**（同一 workload 改一个开关，看 CSV 指标与吞吐变化）
```bash
# A. 关闭 chunked prefill
python -m serving --cluster-config configs/cluster/single_node_single_instance.json \
    --dtype bfloat16 --no-enable-chunked-prefill \
    --dataset workloads/example_trace.jsonl --output outputs/exp_nochunk.csv
# B. 关闭 prefix caching
python -m serving --cluster-config configs/cluster/single_node_single_instance.json \
    --dtype bfloat16 --no-enable-prefix-caching \
    --dataset workloads/example_trace.jsonl --output outputs/exp_noprefix.csv
```

**检查点**：能解释 `max-num-batched-tokens` / `max-num-seqs` / `block-size` 分别卡住了什么；能在日志里指出一次前缀命中，并说明它如何减少了 prefill 计算。

## 3. 性能建模方法学（核心，3–5 天）⭐

这是"仿真建模方法学"的心脏 —— **模拟器的延迟从哪来、准不准取决于这一层**。

**概念铺垫**
- 模拟器不跑 kernel，而是查 profiler 预先测好的**逐层延迟表**。profiler 用 vLLM 内置 `layerwise_profile()` 抓真实 CUDA kernel 计时。
- **单卡模拟 TP**：任意 TP degree 都在 1 张 GPU 上 profile，通过 `hf_overrides` 把 `hidden_size`/`num_heads` 等按 TP 切分来模拟每卡形状；真正的 collective 交给 ASTRA-Sim。
- 产物：`profiler/perf/<hw>/<model>/<variant>/tp<N>/{dense,per_sequence,attention,moe,skew,skew_fit}.csv` + `meta.yaml`。延迟单位是**微秒**，加载时 ×1000 转纳秒。

**四类查表（`trace_generator.py`）**
- `_load_perf_db()` `trace_generator.py:326`：解析 variant、载 meta、载各类 CSV。
- dense（按 token 线性）/ per_sequence（按请求数线性）/ moe（按 `(local_tokens, activated_experts)`，tp=1 profile）。
- attention 4D 查表：`trace_generator.py:759` `_lookup_attention`（在 `(prefill_chunk, n_decode)` 上最近邻、`(kv_prefill, kv_decode)` 上双线性）。
- **skew 修正**：`trace_generator.py:714` `_lookup_attention_with_skew`。异构 decode batch 里 kv 长度不均会让 FlashAttention varlen kernel 付出 tile padding / SM 不均代价，用一个归一化 `alpha∈[0,1]` 在 mean→max 两次查表间插值。`alpha` 从 `meta.yaml::skew_fit` 的分桶表里查。

**建模映射：CSV 如何变成 trace 里的 `comp_time`**
- 规范层名表（simulator ↔ profiler 一一对应）见 `AGENTS.md` 的 "Canonical layer names" 小节：`embedding/qkv_proj/attention/o_proj/gate_up_proj/down_proj/moe/lm_head/sampler …`。
- `trace_generator.py:1144` `_emit_sequence()` 按模型结构 yaml 的 `sequence:` 逐层走，查表填 `comp_time`，并在 `o_proj`/`down_proj` 后挂 TP ALLREDUCE。

**动手**
```bash
# 直接读这些表，建立"数字→延迟"的直觉
column -s, -t profiler/perf/RTXPRO6000/meta-llama/Llama-3.1-8B/bf16/tp1/dense.csv | head
column -s, -t profiler/perf/RTXPRO6000/meta-llama/Llama-3.1-8B/bf16/tp1/attention.csv | head
cat profiler/perf/RTXPRO6000/meta-llama/Llama-3.1-8B/bf16/tp1/../meta.yaml | head -60
```
把某次运行生成的 trace 文件留下来，逐行对照：某层的 `comp_time` 能不能从对应 CSV 手动查出来。

**检查点**：能讲清 attention 为什么要 4D + skew 修正而 dense 只需 1D；能指出 profiler 与 simulator 是靠"同一份 `profiler/models/<model_type>.yaml` 的 sequence"对齐的。

## 4. 并行与网络：ASTRA-Sim 侧（3–4 天）

**概念铺垫**
- **TP**（张量并行，层内切分，通信 = ALLREDUCE）/ **PP**（流水并行）/ **EP**（专家并行，MoE，通信 = ALLTOALL）/ **DP**（数据并行，多实例同 `dp_group` 共享专家）。
- ASTRA-Sim 负责把这些 collective 在给定拓扑/带宽下算成 cycle。

**建模侧：cluster config → 三份 ASTRA-Sim 输入**
- `config_builder.py:28` `_prepare_input_config_paths()` 生成：`network.yml`（拓扑/带宽）、`system.json`（调度策略/内存带宽）、`memory_expansion.json`（远端 CPU 内存）。
- 并行度推断 `config_builder.py:55` `_resolve_parallelism()`；DP 组 `config_builder.py:132`；2D 拓扑维度 `config_builder.py:192` `_compute_network_dims()`。
- trace 里的通信编码：`comm_type` 可带维度作用域，如 `ALLREDUCE:1,0` / `ALLTOALL:0,1`，对应 ASTRA-Sim 的 `involved_dim` BoolList（多维拓扑上只在某维通信）。
- ⚠️ ASTRA-Sim 收的是 collective 的**总数据量**（它内部再除以 N），别传 per-NPU 大小。

**动手**：跑多实例场景，`--log-level INFO` 观察通信。
```bash
python -m serving --cluster-config configs/cluster/single_node_multi_instance.json \
    --dtype bfloat16 --dataset workloads/example_trace.jsonl \
    --output outputs/exp_multi.csv --num-req 10
```
运行后看 `astra-sim/inputs/{network,system,memory}/` 里被 `config_builder` 生成/覆写的文件（注意：每次运行都会重写，别手改指望它留存）。

**检查点**：给定一个 cluster config，能预测它会生成怎样的拓扑维度、哪些层会触发 ALLREDUCE/ALLTOALL。

## 7. 会改：扩展仿真器（能力目标）

对照 `AGENTS.md` 的 "Adding a New Model & Hardware" 与 "Common Pitfalls"。三种扩展由易到难：

1. **加新模型（同架构族）**：把 HF `config.json` 子集放到 `configs/model/<org>/<name>.json`，若 `model_type` 已在 `profiler/models/` 五个 yaml（`llama/qwen3/qwen3_moe/mixtral/phimoe`）之列，simulator 无需改代码。
2. **加新硬件 / 新 dtype（如补 fp16）**：编辑 `profiler/profile.sh` 的 `MODEL/HARDWARE/TP_DEGREES`，在 vLLM 容器里 `./profiler/profile.sh`，产出新的 `perf/<hw>/<model>/<variant>/` —— 这正是修掉"坑 2"的正道。
3. **加新机制 / 新层结构**：新 `model_type` → 加 `profiler/models/<type>.yaml`；新块结构 → 扩 `trace_generator.py` 的 sequence walker / `TP_ALLREDUCE_AFTER`；非常规张量形状 → 扩 `memory_model.py` 的 `calculate_sizes`。

**避坑清单（务必读 `AGENTS.md` 原文）**：首/末层必须用 `REMOTE`（否则 Chakra 建 MEM_LOAD/STORE 失败）；层名必须是 vLLM 规范名且出现在 yaml catalog；CSV 存微秒；不要手改 `astra-sim/inputs/`（每次运行被 `config_builder` 重写）；不要假设 `hidden_size == num_heads*head_dim`（用显式 `head_dim`）。

**检查点（毕业作业）**：用 profiler 给现有硬件补出 `fp16` variant，让 README 里 `--dtype float16` 的原始示例能跑通；或给一个新的小模型加 `configs/model/` 配置并跑起来。
